# BUG-001 — Contribution amount accepts more than two decimal places

| Field | Value |
|---|---|
| **Status** | Open (known defect, tracked by an `xfail(strict=True)` test) |
| **Severity** | Major — financial data integrity |
| **Priority** | P2 |
| **Component** | `POST /contributions` |
| **Rule violated** | R3 — amount must have at most 2 decimal places |
| **Found by** | `tests/api/test_contributions.py::test_amount_with_more_than_two_decimals_is_rejected` |
| **Environment** | Provident Fund Demo API 1.0.0, Python 3.12, local |

## Steps to reproduce

1. Sign in: `POST /auth/login` with `tester / Passw0rd!`
2. Register a member (any valid payload) and note its `member_id`
3. Send:

```http
POST /contributions
Authorization: Bearer <token>
Content-Type: application/json

{"member_id": "M00001", "period": "2026-09", "contributor": "employee", "amount": 100.005}
```

## Expected result

`422 Unprocessable Entity` — the amount cannot be represented in MOP (smallest unit 0.01).

## Actual result

`201 Created`. The record stores `100.005`. The balance endpoint then rounds to two decimals,
so the stored ledger and the displayed balance can disagree once several such amounts are summed.

## Impact

Sub-cent amounts make reconciliation against bank statements fail and can produce rounding
differences in member statements and regulatory reports.

## Root cause (analysis)

`ContributionCreate.amount` is declared as `float` with only `gt=0, le=100000` constraints.
No decimal-place validation exists, and `float` cannot represent many decimal values exactly.

## Suggested fix

Use `Decimal` with `decimal_places=2` (e.g. `condecimal(gt=0, le=100000, decimal_places=2)`)
and store money as `Decimal` or integer cents end-to-end.

## Verification once fixed

The three `xfail` cases will start passing. Because the marker is `strict=True`, pytest will then
report **XPASS(strict) → FAILED**, forcing the team to remove the marker and close this bug —
so a fixed bug can never be forgotten silently.
